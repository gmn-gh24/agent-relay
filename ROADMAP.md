# Roadmap

What is planned, in rough order of value. Nothing here is promised or dated: an item moves to
[CHANGELOG.md](CHANGELOG.md) when it ships, and is removed from this file. To suggest or argue for an item, open an
issue.

## Direction

What stays unique about agent-relay, and so is not up for change: a shared folder as the only transport; agents of
different products on different machines under one coordinator; written assignments with approval tiers and owner
cards; a room that is treated as untrusted.

- The trust boundary and the tamper check of the feed stay.
- The threat model is "a confused or prompt-injected agent", not "a skilled attacker with write access". Attacks that
  need deliberate skill (races, planted links beyond what is covered) are written down as known limits. See
  [SECURITY.md](SECURITY.md).
- Claude Code's own cross-session and team features are not a replacement for a room: they cover Claude-only work
  inside one account. A feature request for distributed agent teams in Claude Code
  (<https://github.com/anthropics/claude-code/issues/79507>) would cover the Claude-only half if it ships.

## Next: supply chain

A checksum manifest (`MANIFEST.sha256`) for what a room is built from: `assets/room-package/`, `scripts/*.ps1`,
`RelayCommon.psm1`, the `scripts/*.json` tables and `hooks/*.ts*`.

- Generated by script (sorted ordinal paths, SHA-256, LF, ASCII), never by hand; a static-gate check recomputes it
  and fails on drift.
- Checked before a room is built or updated (refuse and name the file on a mismatch) and by the tamper check
  (a damaged canonical copy is reported, not restored from). The manifest is read from this PC's own copy, never from
  the room.
- Enforced for installed copies only; a working copy only reports, or the dev folder fails its own check on every
  edit.
- Published also as an attested release asset (GitHub build provenance), so a copy can be checked against
  something the repository cannot silently rewrite. `release.yml` fails if the two differ. The in-plugin part comes
  first; the attestation is an add-on.

## For consideration

- **Developer Certificate of Origin.** A `Signed-off-by:` line on each commit (`git commit -s`), said in
  `CONTRIBUTING.md` and optionally checked in CI. It adds a paper trail for outside contributions at small cost.
  Not needed while the project has one maintainer and an MIT license with no outside work; decide if contributions
  grow. It would apply to new commits only.

- **Enforced file ownership.** Today "one owner per file" (`references/multi-builder.md`) is a plan rule plus the
  self-audit; nothing stops an agent from editing a file it does not own. The coordinator already records each
  agent's files in the plan, so the guard could flag or refuse an edit outside them. A per-file writer lock was
  suggested for the shared folder; the room folder needs none (each agent writes its own message files), and a lock
  on project files would be advisory like the plan rule. Revisit if a real room shows a collision the self-audit
  missed; it overlaps the dropped "file reservations" item below.

- **Compaction hints from the coordinator.** A remote agent that stays in a room for hours carries the whole of
  its earlier tasks in its context: it gets slower and dearer per turn, drifts back to an old subject, and at some
  point its product compacts by itself, often in the middle of a task. The coordinator knows the good moments and
  the agent does not, so the coordinator could tell the agent when to compact (or to start over with a clean
  context), as an instruction in a message. To evaluate, not yet to build, and only if and when two things hold
  for an agent's kind: its product accepts a command that comes from the coordinator, and it has a compact
  command or something like it (the name differs outside Claude Code). Until both hold for a kind, nothing is
  sent to agents of that kind.
  - *When.* (1) At a task boundary: a report was accepted and the next assignment is on another subject, another
    part of the code or another work kind. (2) After a long run on one thing: many messages or hours on one
    assignment, several rejected reports in a row, or signs of lost context (a question the assignment already
    answers, a repeated mistake). (3) Before a large assignment, so it starts with room. Never in the middle of a
    task, while a request of the agent waits for an answer, or while the agent holds uncommitted work.
  - *What the coordinator can see.* Only what the room shows: messages and reports per agent, time on the
    assignment, the number of assignments since the agent joined. It cannot see an agent's token count or how
    full its context is. An optional context figure in the agent's heartbeat or report would be an agent's own
    claim: good for a hint, never for a decision of the coordinator's PC (see the trust boundary).
  - *The precondition.* Today compaction is in most products a command the person at the seat types (`/compact`
    in Claude Code, a like command elsewhere), not something the model can run on itself, and a message from the
    coordinator is text the agent reads, not a command its product runs. So this item waits for the products.
    Record per kind in `scripts/agent-kinds.json` whether the kind takes a command from outside its session and
    what its compact command is called; the coordinator sends the hint only to a kind that has both, and the
    wording names that kind's own command. A kind without them is left alone: no line for its user to type, and
    no forced new session as a substitute.
  - *What must survive.* Before it compacts, the agent writes down what the room does not hold: the state of
    work in progress, decisions it made, files it touched, what it was about to do. A handover note in its
    report or a note to itself in the room covers this, and the instruction asks for it first. After the
    compaction the agent runs `start` and `wait` and reads its note.
  - *Form.* Either wording in `references/coordinating.md` and the assignment template (the coordinator adds a
    line by judgment, no tool change), or a marker of its own on an assignment or a note that `relay.ps1` prints
    as a `NEXT:` line (a room package version bump). Start with the wording; add the marker only if real rooms
    show the wording is ignored.
  - *To settle.* The thresholds and whether they are room settings; whether the owner is asked first or only
    told; how the coordinator learns that the compaction happened (a new introduction, a line in the next
    report) and what it does when it did not; and whether a compaction at the wrong time costs more than it
    saves, since the agent reads its files again afterwards. Measure on one long real room before deciding.

## Looked at and dropped

- Task dependencies that unblock by themselves: the plan already has `depends`, a `blocked` status and a cycle
  check.
- File reservations with a pre-commit guard: one owner per file in the plan and the self-audit cover it.
- A2A, mTLS federation, an HTTP server: transports that agent-relay chose not to need.
- A web view: the pane and the feed in a terminal do this.
- Waking an agent through its session's inbox socket: works for Claude Code only, where a background wait already
  wakes the agent.
- `sh` and `ssh`: postponed by the owner, with no plan; see "Status and limitations" in [README.md](README.md).
